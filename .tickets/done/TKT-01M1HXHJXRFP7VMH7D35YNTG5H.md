## Description

You cannot run `list --type epic` in a forge web UI. A directory is the only query a file browser hands you for free, which is the argument that keeps pulling toward partitioning the store by type. A generated index buys the same view without making a reclassification a rename.

Proposal: `.tickets/epics.md`, a generated Markdown table of the epics in the store, regenerated by `check --fix` and reported as stale by `check`.

All three decisions are settled and recorded at the end of plan section 15. What follows states the answers and their reasoning. The plan is the record.

### The precedent is already in section 4

`README.md` is generated at `init`, explains the store to a human who finds it in a diff, and is not read by the tool. `epics.md` is that same category of file: written for a person, never a source of truth, safe to delete and rebuild.

The difference is refresh. `README.md` is written once and never has to be true again. An index has to stay true, so it needs a staleness story or it becomes a file that lies confidently.

### Settled: which epics appear is an exclusion, not a list

`done` and `archived` are left out. Everything else appears, which today means `draft`, `ready`, `in-progress`, `blocked`, and `review`.

Stating it as an exclusion is the part that matters. An inclusion list silently drops any status added later, and whether this format grows one is a live question in section 15 under custom statuses. An exclusion survives that change with no edit.

Drafts appearing is also right on its own terms. A draft epic is a decomposition somebody is actively writing, which is the thing a person browsing the forge most wants to see, and the status column carries the distinction for anyone who cares.

### Settled: epics only, and a second view is a plan change

The index renders epics and nothing else. Adding a view is a change to `docs/plan.md` and to the code, never a key in `config.yml`.

Configurable views put queries into configuration, which the tool then has to validate, and every consumer then wants its own file written into somebody else's store. The generator may be reusable inside the binary, and probably should be, because the working set is the obvious second candidate. What it renders is not the store's choice to make.

### Settled: a stale index is a warning

The tradeoff this looked like does not exist. `--strict` promotes warnings to errors, per 10.3, and CI runs `check --strict`, so a warning is enforced exactly as hard as an error everywhere enforcement actually happens. Nothing is lost by not calling it an error.

What is gained is the line: a derived file falling behind is not a malformed store. That is the same line that keeps "this ticket is late" out of `check` entirely, on TKT-01M1HPCVRK1989NDNR9PJS36S4.

Severity also does not gate repair, which is what makes the warning free rather than merely defensible. `planRepairs` recomputes where each file belongs rather than walking the findings, so a warning is exactly as repairable as an error.

TKT-01M1HXPJP7EGJVC2J7GC6Y887E carries the same answer. The two cannot diverge.

### check --fix owns the regeneration

Regeneration must not happen on every mutation that touches an epic. That rebuilds the hot file `blocks_on` exists to avoid: two agents changing two unrelated epics each rewrite `epics.md` and collide on a file neither of them was editing.

`check` reporting the staleness and `check --fix` repairing it fits what already shipped for `filename_id_mismatch` and `archive_location_mismatch`, and `just ci` runs `check --strict` on every PR, so the window in which the file can be wrong ends at the next CI run.

A derived file's merge conflict also has a mechanical resolution that a semantic conflict does not. Take either side, run `check --fix`, commit. That is worth stating in the plan, because a shared generated file looks like a bad idea until you notice its conflicts are free.

### Known implementation cost: Repair is a rename

A `Repair` today carries `Codes`, `Ticket`, `From`, and `To`. It describes moving a file. Rewriting a generated file is not a move, so this needs either a second repair kind or a widened shape, and `FixResult` and the `pathsChanged` reporting in 10.3 follow whichever way it goes.

That is an implementation cost and not a further format decision. It is recorded here so the shape is a known cost going in rather than a surprise found halfway.

### The row contents decide how often it rots

A row of ID, title, status, and a repository-relative link can only be staled by a mutation to an epic.

A row carrying child counts, blocking state, or a due date can be staled by any ticket in the store changing status, which means CI goes red on a commit that touched no epic at all. Minimal rows are not a simplification here, they are what keeps the staleness surface proportional to the thing being indexed.

### What this does not become

`epics.md` is not a store marker. TKT-01M1HJTCYTZZHGGPCXT2SAJMFR is settling what a directory must contain to count as a store, and this file must not become part of that answer, for the same reason `README.md` is not: a store with the file deleted is a store with a stale index, not a directory that stops being a store.

It is also not read by the tool, ever. Nothing resolves an ID through it, no query consults it, and `check` compares it against the tickets rather than trusting it.

### Tension with TKT-01M1HVMQQQE3K6VZG7793RXVXN

That ticket proposes partitioning the store into status directories so `tickets/` holds the working set. This index chases the same goal, seeing what matters without running the tool, and gets there with no renames, no path churn, and no `git log --follow`.

If this ships, most of the motivation for the directory partition is gone. The two should be decided together rather than one quietly obsoleting the other.

## Summary

Shipped in PR #45. `.tickets/epics.md` is generated: a table of the open epics, each row linking to its file. `check` reports `epics_index_stale` when it disagrees with the tickets, `check --fix` rewrites it, and `init` writes it so a fresh store is not born stale.

All three settled decisions came through intact. The filter is an exclusion of `done` and `archived`, so a status added to 6.1 later appears with no edit. Epics only, with no configuration key. Stale is a warning, which `--strict` promotes, so CI enforces it exactly as hard as an error.

The known cost landed as predicted: `Repair` gained `Kind`, either `move` or `rewrite`. A rewrite nulls `ticket` and `from` in the JSON and names the file in `to`. Plan 12.4 records the break.

Two rules turned out to be easy to get subtly wrong, and both now have mutation-verified tests. Rows sort by ID, because an index rendered in store order would come back different on a different machine and report itself stale forever. The link comes from `statusDir(t.Status)` rather than the file's current path, because `Fix` plans this rewrite before it moves anything.

Every store fixture gained an `epics.md`. A fixture without one trips a warning it was not written to cover, which `testdata/README.md` now says.

Two things surfaced on the way. This repository's own `.tickets/README.md` was still the pre-partition version, drifted since PR #42 because nothing checks it; it is now what `init` writes. And the tension with TKT-01M1HVMQ resolved by both shipping: the directories answer status and this file answers type, which is why neither had to win.
