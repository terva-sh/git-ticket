## Description

You cannot run `list --type epic` in a forge web UI. A directory is the only query a file browser hands you for free, which is the argument that keeps pulling toward partitioning the store by type. A generated index buys the same view without making a reclassification a rename.

Proposal: `.tickets/epics.md`, a generated Markdown table of the epics in the store, regenerated by `check --fix` and reported as stale by `check`.

### The precedent is already in section 4

`README.md` is generated at `init`, explains the store to a human who finds it in a diff, and is not read by the tool. `epics.md` is that same category of file: written for a person, never a source of truth, safe to delete and rebuild.

The difference is refresh. `README.md` is written once and never has to be true again. An index has to stay true, so it needs a staleness story or it becomes a file that lies confidently.

### check --fix owns the regeneration

Regeneration must not happen on every mutation that touches an epic. That rebuilds the hot file `blocks_on` exists to avoid: two agents changing two unrelated epics each rewrite `epics.md` and collide on a file neither of them was editing.

`check` reporting `index_stale` and `check --fix` regenerating fits what already shipped. `filename_id_mismatch` and `archive_location_mismatch` are repaired the same way, `just ci` runs `check --strict` on every PR, so the window in which the file can be wrong ends at the next CI run.

A derived file's merge conflict also has a mechanical resolution that a semantic conflict does not. Take either side, run `check --fix`, commit. That is worth stating in the plan, because a shared generated file looks like a bad idea until you notice its conflicts are free.

### The row contents decide how often it rots

A row of ID, title, status, and a repository-relative link can only be staled by a mutation to an epic.

A row carrying child counts, blocking state, or a due date can be staled by any ticket in the store changing status, which means `check --strict` goes red on a commit that touched no epic at all. Minimal rows are not a simplification here, they are what keeps the staleness surface proportional to the thing being indexed.

### Decision 1: which epics appear

Filed as: not done, not archived. Open: whether `draft` appears.

A draft epic is a decomposition somebody is actively writing, which is arguably the thing a person most wants to see when browsing the forge. Excluding it hides planned work. Including it and letting the status column carry the distinction is the cheaper answer, and it means the filter is one rule, not a list of statuses that has to be revisited whenever section 6 gains one.

### Decision 2: epics only, or a general index mechanism

Option A, one built-in view of epics, and a plan sentence explicitly refusing configurable views. Narrow, finishable, and it does not grow into a templating system.

Option B, a mechanism that renders a named query to a named file. More useful and considerably more surface, and every consumer then wants their own view in the store.

Option A is the one to ship. If a second view is ever wanted, the working set is the obvious candidate, and that is a reason to keep the generator's shape reusable internally without exposing configuration.

### Decision 3: does a stale index fail check --strict

Failing is consistent with the other findings and makes CI the enforcement, in the way gofmt is enforced. It also means a PR that changes an epic's status goes red until somebody regenerates, which is friction on exactly the workflow this is meant to serve.

Warning instead leaves the file quietly wrong, which is the failure mode that makes a generated index worse than no index.

### What this does not become

`epics.md` is not a store marker. `TKT-01M1HJTC` is settling what a directory must contain to count as a store, and this file must not become part of that answer, for the same reason `README.md` is not: a store with the file deleted is a store with a stale index, not a directory that stops being a store.

It is also not read by the tool, ever. Nothing resolves an ID through it, no query consults it, and `check` compares it against the tickets rather than trusting it.

### Tension with TKT-01M1HVMQ

That ticket proposes partitioning the store into status directories so `tickets/` holds the working set. This index chases the same goal, seeing what matters without running the tool, and gets there with no renames, no path churn, and no `git log --follow`.

If this ships, most of the motivation for the directory partition is gone. The two should be decided together rather than one quietly obsoleting the other.

## Acceptance criteria

- [ ] All three decisions in the description are settled and recorded in docs/plan.md before any code lands.
- [ ] check reports a stale index and check --fix regenerates it.
- [ ] No mutation writes epics.md. Only check --fix does.
- [ ] epics.md is never read by the tool and never counts toward what makes a directory a store.
- [ ] Section 4 documents the file beside README.md.
- [ ] A corpus fixture covers a store with a stale index and one with a current index.
