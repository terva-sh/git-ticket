# Handoff: git-ticket Phase 3, the terva side

For an agent or engineer working in the terva repository. It assumes no
knowledge of git-ticket. Everything here is either published and verifiable or
marked as a decision you own.

Written from the git-ticket side, which owns the format, the library, and the
CLI. It does not own anything under terva, and that is the point of handing you
a document instead of a commit.

## The boundary

git-ticket owns the format, the store, validation, the CLI, and the two public
Go packages. It cuts the releases. Nothing in it imports terva.

terva owns everything under terva: the command, the tools, the board, the
permission wiring, and the terva-side plan. git-ticket does not write there.

If terva needs the format or the library to change, that is a git-ticket
change, and the section "Asking for a library change" below says how to raise
it. Do not work around a library gap with a second parser. The whole design of
this integration is that there is exactly one implementation of the format.

## What already exists, and is published

`github.com/terva-sh/git-ticket`, tagged **`v0.2.0`**. One dependency,
`gopkg.in/yaml.v3`. `go` directive `1.25`, so it does not constrain terva,
which declares `1.25.0`.

Two importable packages, and you will want both for different jobs.

| Package | Gives you | Use it for |
|---|---|---|
| `.../git-ticket/cli` | `Run(args []string, env Env) int` and `Env` | `terva ticket`, the command |
| `.../git-ticket/ticket` | The store and typed values | The `ticket_*` tools and the board |

`cli` exports exactly two identifiers. That is the whole API.

What the format gives you: Markdown tickets with YAML frontmatter in
`.tickets/` in the user's repository, so the work record travels with the
branch and merges through ordinary review. 24 CLI commands. Seven JSON envelope
kinds. `check` with 14 error codes and 5 warning codes. Statuses are `draft`,
`ready`, `in-progress`, `blocked`, `review`, `done`, `archived`. Types are
`task`, `bug`, `chore`, `spike`, `epic`.

## The work, in four slices

Ordered so each is useful alone. Nothing in git-ticket blocks any of them.

### Slice 1: the dependency and the command

Require `github.com/terva-sh/git-ticket v0.2.0`. Add `terva ticket` as a
delegation:

```go
import "github.com/terva-sh/git-ticket/cli"

code := cli.Run(args, cli.Env{
    Dir:    projectDir, // the user's repository, not terva's cwd
    Getenv: os.Getenv,
    Stdout: out,
    Stderr: errOut,
})
```

That is the whole implementation, and it yields all 24 commands, human and
`--json` output, and the documented exit statuses. A command added upstream
appears in `terva ticket` on the next module bump with no terva change.

`Env.Dir` is the field that matters: the store is discovered from the path you
pass, not from the process working directory.

Do not hand-write command wrappers. If `cli.Run` cannot do something you need,
that is a git-ticket bug, and see below.

### Slice 2: the five read tools

`ticket_list`, `ticket_search`, `ticket_get`, `ticket_ready`, `ticket_check`.
All `local-read`, so they carry no mutation authority and are cheap to review.

```go
st, err := ticket.Discover(dir)        // nil error means a store exists
tickets, err := st.List(ctx, ticket.Filter{Status: []string{"ready"}})
hits, err := st.Search(ctx, ticket.Query{Text: "...", Regex: false})
one, err := st.Get(ctx, "TKT-01M1FCGPE")   // ID prefixes resolve
ready, err := st.Ready(ctx)
report, err := st.Check(ctx)
```

Register the tools only when a store exists. `ticket.Discover(dir)` is the
probe, and lazy tool visibility is the mechanism. A repository with no
`.tickets/` should pay no schema cost. Visibility is not authority.

Pass a real context. `Store` methods call `ctx.Err()`, so a nil context panics.
That is correct Go and it caught me once.

### Slice 3: the five write tools

`ticket_create`, `ticket_update`, `ticket_transition`, `ticket_claim`,
`ticket_comment`. All `workspace-mutation`.

```go
res, err := st.Apply(ctx, ref, ticket.SetStatus{Status: "in-progress"}, ticket.ApplyOptions{
    IfRevision: t.Revision,                       // read it off the ticket first
    Actor:      ticket.Actor{ID: "agent:terva/mieli"},
})
```

`SetStatus.Reason` is required entering `blocked` and reopening from `done`,
and accepted anywhere else. It lands in both `status_reason`, which a query
reads back, and a `Notes` entry, which survives the transition that clears the
field. Your `ticket_transition` tool should expose it and enforce nothing:
`Apply` rejects a missing reason itself.

Mutations are typed structs, not a struct of pointers, so "set the title to
empty" and "do not touch the title" cannot be confused. `SetStatus`,
`SetTitle`, `SetPriority`, `AddLabel`, `RemoveLabel`, `ClaimTicket`,
`ReleaseClaim`, `AppendNote`, `AppendComment`, `SetSummary`, and the rest are
all exported.

Two things this slice must get right, and both are in the plan for a reason.

**Classify these `workspace-mutation`, never `local-data`.**
`IsReadOnlyAuthority` auto-allows `local-read` and `local-data`, and
`local-data` means the tool's own directory under `$TERVA_HOME`. A ticket store
lives in the user's repository and lands in their next commit. Gate it like
`write` and `edit`.

**Mark `IfRevision` required in the tool schema**, even though the library
leaves it optional. The library is lenient so a person typing one command is
not forced into a read-then-write dance. Agents read before they write anyway,
and multi-agent is where the races happen. A stale precondition returns
`stale_revision`; surface that as a model-readable refusal naming the current
revision so the agent re-reads instead of retrying blindly.

Identity is `Actor{ID, Name}`. The store this repository keeps uses
`human:name` for a person and `agent:terva/persona` for an agent. Identity is
optional in the format, so git-ticket never requires terva to be present.

### Slice 4: the board

A kanban view: columns by status, cards for tickets, pointer interaction.
In-tree Preact under `packages/agent/web/client/src/`, over ctrlproto.

This slice is why the whole surface is core rather than an extension, and the
reasoning is easy to get backwards. An extension **can** own a panel, and it
**does** render in the web client: `PanelBody` in `app.tsx` draws it and
forwards keystrokes through `surface.action`. But the panel model is lines of
text in both frontends, `(p.lines ?? []).map(stripAnsi).join('\n')`. An
extension gets a monospace blob and key events, and cannot emit columns, cards,
or pointer targets. A text board is an extension. A real one is not.

Read through the same library as the tools. Do not parse a ticket file. Moving
a card is a status transition through `Store.Apply`, with the same revision
precondition and the same permission class as `ticket_transition`. A drag is a
mutation, and being a mouse gesture does not change its authority.

## What you do not need from git-ticket

Two things look like gaps and are not, so do not file them upstream.

**Paging.** `Filter` and `Query` have no offset or limit, and `List` and
`Search` return the full set. Slice it in terva. Reading every file on every
call is the documented design at this format's scale, hundreds to a few
thousand tickets, and an index is deliberately deferred. `standard-tools.md`
still requires your tools to cap and page their results, so do that at the tool
boundary.

**Revision access.** `Ticket.Revision` and `Ticket.Path` are already on the
struct, so the read-then-write cycle needs no extra call.

## Decisions already settled

Do not relitigate these without new information. Each cost real argument.

**Core, not an extension.** `standard-tools.md` defaults to extension-first,
and `terva-tasks` is the precedent. That default exists to avoid committing
core surface to an unproven design, and git-ticket is not unproven: written
format, 24-command CLI, fixture corpus, green build, two tags, and a store its
own repository runs its work through. Two of `standard-tools.md`'s own
exceptions also apply, since the tools replace a `bash` pattern and the board
needs harness-level UI.

**`terva ticket` mirrors everything, by embedding.** The alternative options
were mirroring a subset and shelling out to the `git-ticket` binary. The subset
makes users learn two vocabularies, and shelling out fails on packaging,
because terva ships as a small static binary and a harness cannot depend on a
tool it does not ship. Embedding also makes "no second parser" a fact instead
of a discipline.

**Singular names.** `terva ticket` and `ticket_*`, matching `git ticket`.
Directories stay plural, so the store is `.tickets/`. The older proposal says
`terva tickets` and `tickets_*`; those spellings are superseded.

**Ticket tools and task tools stay separate families.** `ticket_*` coordinates
project work that outlives the session. `task_*` coordinates one agent's turn
sequence. Different lifetimes, and they must stay distinguishable.

**No implicit commit, and no remote operation.** A mutation writes files and
stops. Publishing is the user's ordinary Git workflow.

## Open questions you own

1. **Does the integration ship off by default?** terva's `AGENTS.md` says a
   feature that changes authority or safety ships off and is enabled from
   user-layer configuration only. Adding `workspace-mutation` tools is arguably
   ordinary tool surface rather than a change to the authority model, and
   store-gated registration is already a strong gate. Decide before slice 3. If
   you want a config key, decide whether it gates the write tools alone or the
   whole family.

2. **`ticket_deps` and `ticket_files`.** Both are read-only queries the CLI
   already has. `files PATH` lists tickets referencing a path, which suits an
   agent well. Left out of the first ten rather than rejected. Add them, or
   fold them into `ticket_get` and `ticket_list`.

3. **What a card shows.** Deferred to slice 4 deliberately, because using the
   tools first is cheaper than guessing.

## The parent hierarchy, settled

The board will want to show an epic's children, and it can. This was the one
cross-repo dependency in the original handoff, listed there as unsettled. It is
done.

In the library, which is what your tools use:

```go
kids, err := st.List(ctx, ticket.Filter{Parent: []string{epicID}})
roots, err := st.List(ctx, ticket.Filter{Parent: []string{""}})
```

An empty string means "has no parent", which is your board's top level. The CLI
spells the same two `list --parent ID` and `list --parent none`.

Direct children only, and that costs you nothing. `List` already returns every
ticket with its `Parent`, so one unfiltered call gives you every edge and you
build the whole tree yourself. Reach for the filter when you want one epic's
children without walking the store again.

The library resolves nothing: pass a full ID, and an ID the store does not hold
is simply no match. The CLI does resolve, so `--parent` takes a prefix and an
unknown one is `ticket_not_found` rather than an empty list.

`deps` still walks `dependencies` and nothing else. When its answer is empty and
the ticket has children, the human output names the count and points at the
filter. `--json` does not carry that, so nothing in your tool path sees it.

`10.1` did not move. The `ticket-list` envelope still carries exactly
`schemaVersion`, `kind`, and `tickets`, which under 12.4 makes this additive and
therefore a minor release. It is on `main` and needs a tag before you can import
it, so say the word and one gets cut.

## Asking for a library change

Tell the user, or open an issue against git-ticket. Do not patch around it.

Two rules govern the answer. The plan is authoritative, so a format question is
settled in `docs/plan.md` and never in code. And when the plan does not answer
a question, it goes to section 15 as a deferred question rather than being
invented.

The practical consequence for you: a library change means a git-ticket commit,
a tag, and a module bump in terva. That is a round trip, so raise it early.

## Verify the dependency before you build on it

This is a real run, not an illustration. It resolves the published module from
the public proxy with no replace directive:

```go
package main

import (
    "context"
    "fmt"
    "os"

    "github.com/terva-sh/git-ticket/cli"
    "github.com/terva-sh/git-ticket/ticket"
)

func main() {
    repo := os.Args[1]
    env := cli.Env{Dir: repo, Getenv: os.Getenv, Stdout: os.Stdout, Stderr: os.Stderr}

    fmt.Printf("ready exit=%d\n", cli.Run([]string{"ready"}, env))
    fmt.Printf("missing exit=%d (want 1)\n", cli.Run([]string{"show", "TKT-NOPE"}, env))

    st, err := ticket.Discover(repo)
    if err != nil {
        fmt.Println("discover:", err)
        os.Exit(1)
    }
    ready, err := st.Ready(context.Background())
    if err != nil {
        fmt.Println("ready:", err)
        os.Exit(1)
    }
    for _, t := range ready {
        fmt.Printf("  %s  %s  %s\n", t.ID, t.Priority, t.Title)
    }
}
```

```sh
go mod init example.com/probe
go get github.com/terva-sh/git-ticket@v0.2.0
go run . /path/to/a/repo/with/dot-tickets
```

Point it at a checkout of git-ticket itself, which keeps its own tickets in
`.tickets/`, so there is a real store to read.

## Acceptance bar

`standard-tools.md` sets it for a new core tool, and it applies per slice:
implementation under `packages/agent/tools/` registered in `BuildToolRegistry`;
`readOnlyTools` and `builtinTools` classification in
`packages/agent/build/permissions.go`; entries in `toolSummaries`; the authority
class documented in `standard-tools.md`; permission-policy tests covering plan
mode and headless refusal; cap and cursor tests for the list and search tools;
a `row{}` in `packages/agent/help.go` per new flag; `go run
./cmd/terva-i18n-lint` for new user-visible strings; and docs in `docs/cli.md`.
